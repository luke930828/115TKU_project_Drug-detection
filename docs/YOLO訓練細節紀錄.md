# YOLO 影像辨識模型訓練細節紀錄

本文件記錄 YOLO 模組從第一版到目前的訓練過程：資料集演進、增強策略的調整、訓練參數、設備更換（RTX 3050 4GB → RTX 4070 12GB）的影響，以及對照實驗結果與尚未解決的問題。
數字來源是各次訓練留下的 `runs/detect/<實驗名>/args.yaml`、`results.csv` 與訓練主控台輸出；無法從檔案核對的項目，已標註「待確認」。

最後更新：2026-10-18

### 2.1 各版本說明

**v1（3 類）**
- 最初的概念驗證，辨識 cannabis、heroin、cocaine 三種。

- 這個高分反映的是資料集本身很好認，而不是模型比後續版本強；後續版本改用我們自己蒐集、背景與包裝更複雜的真實場景影像，難度完全不同。
- 對應 commit `ec37f78`（2026-03-19）「完成 YOLOv11 訓練與推論測試」。
- 訓練 50 epochs，約 30 分鐘。`patience=100` 在 50 epoch 內不會觸發早停。

**v2（16 類）**
- 類別擴充到 16 類：`botanical_joints, cannabis_like_herbal, cannabis_logo, digital_scale, drug_edible, illicit_packaging, magic_mushroom, medical_bottle, pills_capsules, pills_tablets, substance_crystal, substance_powder, syringe, vape_cartridge, vape_device, ziplock_bag`。
- 對應 commit `db00d34`（2026-08-03）。
- 訓練集 1398 張，**是 Roboflow 匯出時做過 3 倍增強的結果**，真實獨立影像約 466 張（依我們當時的分析推算）。
- 這次的 `args.yaml` 顯示起點是 `runs\detect\drug_prevention_v2\weights\last.pt`，也就是用接續訓練（resume）跑完的。

**v3（15 類）**
- 拿掉 `medical_bottle`，其餘 15 類沿用。

- 最弱的類別：`substance_crystal`（AP50 0.170）與 `syringe`（AP50 0.364），完整 per-class 表見 6.5 節。

**v3 資料加上新增 65 張（2026-10-18）**
- 訓練集 598 張、驗證集 152 張、測試集 76 張，共 826 張。

## 3. 資料集處理

### 3.1 Roboflow 設定

| 階段 | v2 | v3 起 |
|---|---|---|
| Preprocessing | Auto-Orient、Resize 640×640 | Auto-Orient、Resize 640×640（Fit，補黑邊） |
| 匯出時增強（Augmentation） | 有（旋轉、模糊、雜訊等，約 3 倍） | **全部關閉** |
| 匯出格式 | YOLOv8 | YOLOv8 |

### 3.2 為什麼關掉 Roboflow 的匯出增強

- Roboflow 的增強是「烘進硬碟的固定變體」。同一張圖會被衍生成多張，這些衍生圖很像，會讓訓練集的影像數字看起來變多，但資訊量沒有等比例增加。
- YOLO 訓練時本來就會**即時**做增強（見 3.3）。兩邊疊加，等於對同一張圖變形兩次，容易破壞辨識文字與標誌的細節（我們的資料有大量包裝上的文字與 logo）。
- 垂直翻轉（`flipud`）對文字與 logo 有害，Roboflow 與訓練端都不開。
- 代價：關掉之後，樣本少的類別少了「重複曝光」的好處。結晶這種本來就樣本少的類別，有可能因此退步。這是我們目前保留的疑點，尚未用對照實驗驗證，見第 8 節。

### 3.3 訓練時實際生效的即時增強（Ultralytics 預設值）

以下數值取自 v3 的 `args.yaml`，其後所有實驗未覆寫：

| 增強 | 值 | 說明 |
|---|---|---|
| `mosaic` | 1.0 | 四張圖拼成一張；最後 10 個 epoch（`close_mosaic=10`）關閉，讓模型回到真實構圖收斂 |
| `hsv_h / hsv_s / hsv_v` | 0.015 / 0.7 / 0.4 | 色相、飽和度、亮度隨機擾動 |
| `translate` | 0.1 | 平移 |
| `scale` | 0.5 | 縮放 ±50% |
| `fliplr` | 0.5 | 左右翻轉機率 50% |
| `erasing` | 0.4 | 隨機擦除一塊區域，模擬遮擋 |
| `degrees` | 0 | **不旋轉** |
| `flipud / shear / perspective / mixup / copy_paste` | 0 | 全部關閉 |

- 本環境沒有安裝 `albumentations`，所以 Ultralytics 內建的模糊、雜訊類增強**沒有生效**。
- 不旋轉、不模糊是目前的缺口：如果實際拍攝的圖片有傾斜或失焦，模型沒看過這類變化。已列入第 8 節的待辦。

### 3.4 匯入流程的注意事項

- `import_roboflow.py` **不會清空** `data/raw` 與 `data/processed`，只做複製加同名覆蓋。所以每次匯入新版本前，必須先把舊資料夾改名備份，否則兩套不同類別 ID 的檔案會混在同一個 `data.yaml` 底下，造成靜默錯標。
- 類別名稱必須與 `modules/yolo/app/ai_model/scoring.py` 的 `CLASS_WEIGHTS` 的 key 一字不差，名稱對不上匯入會直接報錯。
- 刪除類別一律在 Roboflow 用 Modify Classes 產生新版本，不要手動改檔案，否則後面類別的數字 ID 會錯位。
- Windows 解壓縮 Roboflow 的 zip 時，檔名很長，容易遇到「路徑太長」。要解壓縮到短路徑（例如 `C:\rf`），再搬進專案。

## 4. 訓練參數演進

| 參數 | v1 | v2 | v3 | 最新（4070 主機） |
|---|---|---|---|---|
| 基礎權重 | yolo11n | yolo11n（接續自 last.pt） | yolo11n | yolo11n / yolo11s |
| epochs | 50 | 150 | 150 | 150 |
| patience | 100 | 30 | 30 | 30 |
| batch（實際值） | 16 | 2（AutoBatch 0.3 算出） | 2（AutoBatch 0.3 算出） | n 640：12（AutoBatch）；s 640、n 960：16（指定） |
| workers | 8 | 2 | 2 | 預設 2 |
| imgsz | 640 | 640 | 640 | 640 / 960 |
| optimizer | auto | auto | auto（實際選到 AdamW，lr 約 0.000526） | auto |
| 其他 | `lr0=0.01, lrf=0.01, box=7.5, cls=0.5, dfl=1.5, seed=0, amp=true` 全版本相同 |

說明：
- `patience=30`：mAP50-95 連續 30 個 epoch 沒進步就早停，避免對多數類過擬合。
- `batch=0.3`（AutoBatch）：不是固定數字，而是讓 Ultralytics 自動挑一個「大約佔 30% 顯存」的 batch。這個值在 4 GB 顯卡上很小，見第 5 節。
- `optimizer=auto`：Ultralytics 會依總迭代次數自動選擇優化器，所以不同的 batch 大小會讓總迭代次數不同，進而可能選到不同的優化器與學習率。這是換設備時一個潛在的混淆因素（待確認新主機實際選到什麼）。
- `workers=2`：在原本的 3050 筆電上，預設的 8 個 DataLoader 子行程會因記憶體不足而失敗，所以降到 2。

### 4.2 訓練後的權重管理

- 訓練完成後，`train.py` 會把 `best.pt` 複製到 `modules/yolo/app/models/best.pt`（服務實際載入的位置）。
- 部署前會自動把**既有的 `best.pt` 改名為 `best_backup_<時間戳>.pt`**，不需要手動備份。
- 做對照實驗時要加 `--no-deploy`，這樣不會覆蓋或備份正在使用的 `best.pt`。
- 權重檔（`*.pt`）被 `.gitignore` 排除，**永遠不會經過 git**，要手動交給負責打包的組員（雲端硬碟）。
- 2026-09-10 發現 `deploy_dir` 一直指向舊路徑（`models/`），導致自 2026-08-21 重構以來，訓練部署都寫到沒人讀的位置，已修正。

## 5. 舊設備（RTX 3050 4GB 筆電）的限制

- **batch 被迫很小**：AutoBatch 以 30% 顯存為目標，在 4 GB 卡上只選到 `batch=2`。
- 需要設定環境變數 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，減少顯存碎片造成的第一個 batch 就失敗的問題。
- `workers` 降到 2，避免記憶體不足。
- 150 epochs 約 **1.72 小時**（v3，6203 秒）。
- 這個 batch 規模偏小，對訓練的影響有兩個：每次梯度更新只看 2 張圖，估計很吵（noisy）；BatchNorm 的統計量也不穩定。

## 6. 換設備（RTX 4070 12GB）的影響與對照實驗

### 6.1 新主機環境

| 項目 | 內容 |
|---|---|
| GPU | NVIDIA GeForce RTX 4070，12 GB 顯存 |
| 驅動 | 616.56（CUDA 13.4） |
| 作業系統 | Windows（以 cmd 操作） |
| PyTorch | CUDA 12.8 版（`cu128` 輪子） |
| 連線方式 | DeskIn 遠端桌面 |
| 資料來源 | 在新主機上直接從 Roboflow 下載匯出 zip，不從舊電腦搬圖 |

### 6.2 資料

826 張：train 598、valid 152、test 76（匯入工具的複製張數）。比 v3 多的 65 張全部進訓練集。
但 Ultralytics 在新主機驗證時回報 `Images=150、Instances=740`，與 v3 模型驗證時的 152 張 / 834 框不同，驗證集的實際內容是否變動需要查證（見第 8 節）。

### 6.3 對照實驗結果

全部使用同一份資料，且都加了 `--no-deploy`。

| 實驗名稱 | 基礎模型 | imgsz | batch（實際） | mAP50 | mAP50-95 |
|---|---|---|---|---|---|
| `exp_n_640` | yolo11n | 640 | 12（AutoBatch） | **0.7159** | 0.5254 |
| `exp_s_640` | yolo11s | 640 | 16（指定） | 0.6846 | **0.5278** |
| `exp_n_960` | yolo11n | 960 | 16（指定） | 0.7155 | 0.5243 |

batch 值取自各實驗 `best.pt` 內存的 `train_args`（`args.yaml` 只記錄傳入的 `0.3`，不是實際值）。三組的 batch 不完全相同（12 vs 16），這是對照時的一個小變因，但幅度遠小於與舊機器 `batch=2` 的差距。

### 6.4 如何解讀

**1. 整體指標明顯比 v3 好，但不能全部歸功於資料。**
- v3：mAP50 0.601 → 最新 `exp_n_640`：0.716；mAP50-95 0.433 → 0.525。
- 新增的 65 張只佔訓練集約一成，不太可能單獨造成這種幅度的進步。
- **換設備同時改變了 batch 大小**：舊機器 `batch=2`，新機器 `exp_n_640` 的 AutoBatch 選到 12（大 6 倍）。batch 變大讓梯度更穩定，這很可能是進步的主要原因之一。
- 「資料變多」與「環境變好」混在一起，目前無法拆開。這件事需要用「在新主機上強制 `--batch 2` 重跑」之類的對照才能分辨，尚未做。

**2. 換大一號的模型沒有幫助。**
- n 與 s 的差距：mAP50 差 0.031、mAP50-95 差 0.002，在約 150 張驗證集下這個幅度在隨機波動範圍內，沒有證據顯示 s 比 n 好。
- 每個設定只跑了一次，沒有重複，所以無法估計隨機種子的影響。

**3. 提高解析度沒有幫助。**
- 960 與 640 幾乎相同（差距在小數點第三位）。
- 原因推測：Roboflow 匯出的圖片已經被 Resize 成 640×640，訓練時開到 960 只是把 640 的圖放大，原本被壓掉的細節並不會回來。
- 若要真正驗證高解析度的價值，需要在 Roboflow 把 Resize 也改成 960（或拿掉 Resize）重新匯出。這是推論，沒有實驗支持。

**4. 各類別的結果（見 6.5 節）**
- `substance_crystal` 的 AP50 從 v3 的 0.170 升到 0.479～0.677，三組實驗都明顯改善；`syringe` 也從 0.364 升到 0.405～0.616。這兩類在這一輪補了標註，改善與補標一致，但同時混有換設備（batch）和驗證集不完全相同的因素，不能全部算在補標頭上。
- `magic_mushroom` 沒有改善（0.566 → 0.457～0.481），即使這一輪也補了標註，仍是目前最弱的類別之一。
- 同一個類別在三組實驗之間的 AP 擺動很大，例如 `drug_edible` 0.366～0.718、`pills_tablets` 0.365～0.678、`cannabis_like_herbal` 0.380～0.668。整體 mAP 幾乎相同的 n 640 與 n 960，各類別卻互有高低，顯示驗證集很小時 per-class AP 的雜訊很大，**單一類別的差距不能當作模型好壞的證據**。

**5. 結論**
- 對現有的資料量，模型大小與輸入解析度都沒有帶來一致的整體提升；弱類別的樣本數與標註品質仍是主要限制。
- 因此選擇最小、推論最快的 `yolo11n`（`exp_n_640`）作為交付版本。

## 7. 與風險計分的關係

偵測結果會交給 `modules/yolo/app/ai_model/scoring.py` 換算風險分數，公式為「類別權重 × 該類別最高信心度」，取各類別最大值，再套組合加成，上限 100。因此：

- 弱類別的信心度偏低時，會直接拉低它對分數的貢獻，即使它被偵測到。
- 調高模型信心度（例如加重損失）雖然會讓分數變高，但誤報的信心度也會一起升高，所以我們沒有採用。
- 計分規則本身的調整（降低 `illicit_packaging` 權重、`digital_scale` 組合泛化、`medical_bottle` 移除、NLP 規則 B 的空集合修正）不屬於訓練，記錄在計分相關的程式碼與 commit `2d71294`。
